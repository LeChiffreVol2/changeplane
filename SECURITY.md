# Security policy

ChangePlane's supported boundary is the repository-scoped GitHub autonomous harness described in the README. Managed model spend and merge authority are not supported. Scope-only installations remain in observe mode.

Report a suspected vulnerability privately to the repository owner or through the repository's private security-advisory channel. Do not include GitHub tokens, provider keys, private repository content, or other customer secrets in an issue.

## Security invariants

- GitHub and its branch policy remain the merge authority.
- Autonomous activation requires a repository admin, the GitHub App's read-only Administration permission, and one unambiguous no-bypass default-branch Ruleset with strict required status checks, a `merge_queue` rule, the dedicated-App-owned `ChangePlane / guard` bound to its expected integration ID, and every configured behavioral evidence Check bound to its expected integration ID. The repository job named `ChangePlane guard` is visible operational liveness only; it is not ChangePlane merge authority. A write collaborator cannot inspect or mutate repository secret state.
- The evaluator reads policy from the trusted base revision and binds decisions to an exact head SHA.
- Pull-request jobs execute managed controller bytes from the live default branch. They revalidate the default ref and SHA, pull-request base and head, and checked-out controller immediately before provider access, repair dispatch, and guard completion. Retargeting or default-branch drift fails closed.
- A model can propose a patch but cannot issue `PASS`, approve, publish the required Check, or merge.
- BYOK plaintext is processed only long enough to verify the allowlisted model and seal the key with GitHub's repository public key. It is never persisted, echoed, or logged by ChangePlane.
- A provider key pasted into chat, an issue, a screenshot, or any other non-secret channel is treated as compromised even when repository and build scans are clean. The repository owner must revoke it at the provider, replace the repository Actions Secret with a new key, and verify fail-closed behavior before autonomous work resumes.
- Observe mode never dispatches a repair and never blocks a merge.
- Verify Lite requires expected-publisher behavioral evidence and returns fixable findings to the customer's coding agent without provider, repair-webhook, controller-HMAC, or installation credentials. The managed-v13 candidate reports enforcement active only after read-only GitHub inspection proves that one unambiguous active no-bypass default-branch Ruleset has strict required checks, a `merge_queue` rule, the App-owned guard bound to the dedicated ChangePlane App integration ID, and every configured behavioral evidence Check bound to its expected integration ID. Classic branch protection, split controls across multiple Rulesets, GitHub Actions job success, unknown Ruleset shapes, and ambiguous targeting cannot satisfy this high-assurance state. The installer never mutates Rulesets. This candidate has not yet been deployed or live-validated.
- Autonomous mode intentionally sends bounded failure evidence and text context only from controller-granted paths to the repository owner's selected OpenAI project. The proposal and validation helpers execute only from a trusted-base checkout; the pull-request checkout is treated as data. Observe-only evaluation and the public replay send no repository content to a model provider.
- Autonomous repair cannot modify tests, evidence configuration, dependency manifests, or repository-declared `evidence.protectedPaths`. `.changeplane.json`, `.github/workflows/**`, and `changeplane/**` are unconditional human-review controls that a repository policy cannot remove. The trusted evaluator also materializes nested tests, manifests, configuration files, and both sides of a rename into the effective review set; the signed grant carries that set, and the proposal plus clean-apply validators reject evidence-control edits again.
- The setup PR vendors versioned managed workflows and helpers into the selected repository. Repository-owned edits to reserved managed bytes are never overwritten automatically.
- Repository repair secrets begin inert. Provisioning writes `CHANGEPLANE_REPAIR_ENABLED=false` first and activates only the marker for the exact managed workflow version after a fresh admin check and a fresh proof of the complete Ruleset contract. An older workflow cannot consume a newer activation marker. The controller derives a repository-bound HMAC and the proposal job receives no GitHub token, App key, controller master, Check authority, or push credential.
- A one-time exact-repository Contents-write installation token is minted only after the App-signed grant is claimed and revalidated immediately before a force-with-lease push. The resulting new commit receives its own exact-SHA evaluation; no assurance state is carried across revisions.
- `ChangePlane / review` is read-only, BYOK-gated, and bound to the exact diff. Findings must resolve to changed lines, are capped and deduplicated, and never approve, certify, repair, or contribute PASS.
- `.changeplane/assurance.md` is read only from the trusted default branch. Its repository-owned invariants and policy-pack guidance are untrusted context, not behavioral evidence.
- Agent handback Action outputs and receipt payloads carry findings and revision metadata only. They grant no GitHub credential, repair claim, controller authority, or certification.
- The Assurance Passport binds policy, evaluator, evidence, decision, and fixed authority roles to one base and head revision with a domain-separated SHA-256. Offline verification proves integrity only. Live proof requires a completed exact-head `ChangePlane / guard` from the configured dedicated ChangePlane App, with one exact passport marker and compatible conclusion, re-fetches the latest eligible identified evidence Check and its policy-pinned publisher, re-hashes the trusted-base policy, and compares the current pull request. The passport and proof locator carry no signer, credential, repair claim, approval, Check authority, or merge authority, and claimed agent identity never contributes to PASS. Proof of the App-owned Check alone does not prove that the required no-bypass Ruleset is active or that all configured evidence Checks are publisher-bound there.
- Repository workflows have `actions: read`, `checks: read`, and `id-token: write`, not App-guard publication authority. Actions read is used only to resolve a candidate `github-actions` Check to its exact workflow run and trusted policy path. The hosted publisher accepts only a GitHub-signed OIDC identity for the exact default-branch managed workflow, repository, workflow SHA, event, ref, run ID, and attempt. Before mutable decision inputs are evaluated, the begin request re-fetches the managed tree and current same-repository target and creates one immutable exact-SHA evaluation lease represented by `ChangePlane / guard` in `in_progress`. A repeated begin from the owning run and attempt is idempotent; a competing run or attempt is rejected. The repository workflow's `ChangePlane guard` job remains visible operational liveness only and cannot satisfy ChangePlane guard authority or Ruleset readiness.
- Guard completion must own the same run ID and attempt as the immutable lease. The publisher re-fetches the trusted base, policy, managed tree, target, and latest eligible evidence on the exact head before it may update that same App Check. A changed target, stale completion, missing begin, malformed marker, publisher mismatch, or newer evidence result fails closed. Starting a rerun after the exact-SHA lease completed invalidates the App guard to `action_required` and requires a new commit; it cannot replace or inherit the prior decision on the same SHA. Read-only and `checks:write` installation tokens are minted separately for exactly one repository and only for the request lifetime.
- An enforce-mode `PASS` passport is invalid unless it records `ALL_GUARANTEES_SATISFIED`, at least one evidence Check, behavioral evidence class, and a passing result for every evidence entry. Duplicate passport markers and pull-request receipt/passport binding mismatches are rejected.
- A preview URL is published only when its deployment SHA matches the evaluated head. A stale or unverifiable preview is omitted.
- `merge_group` is evaluated as a separate exact revision and receives a fresh App-owned guard under the same immutable-lease rules. Merge Queue runs publish guard evidence only and never invoke a proposal model or repair controller.
- The repository-level Agentic SDLC view is a pure projection of already-verified runtime facts. The per-revision spine in this candidate is a signed-out synthetic explainer, not a hosted receipt field or live evidence claim. Neither contributes to `PASS`, authorizes repair, carries trust across revisions, or treats comments, agent identity, model review, risk labels, or deployment presence as behavioral evidence. The helper requires intent, diff observation, and passing behavioral evidence independently bound to the current full SHA; review and deployment provenance are separately SHA-matched. It invalidates the revision-level view on a new commit, leaves Merge with GitHub, and leaves Operate outside ChangePlane.
- Verify and Autonomous cannot evaluate to `PASS` with an empty required-Check set. The hosted runtime and trusted vendored harness share a strict required-Check contract: publisher-bound entries contain `name` and a lowercase GitHub App `appSlug`; a `github-actions` publisher in enforce mode must also declare one exact `.github/workflows/*.yml` or `.yaml` `workflowPath`, which is resolved through the Check's GitHub Actions run and bound to the exact head. Other App publishers cannot declare `workflowPath`. Malformed, unbound, stale, non-latest, or empty enforce-mode evidence fails closed before assurance is projected, evaluated, or published.

The dedicated-App guard lifecycle, workflow-bound evidence checks, and Ruleset readiness contract above are implemented in the managed-v13 candidate and covered by local automated tests. They have not been deployed or exercised in a protected v13 canary. Historical v9 evidence used a legacy `github-actions` guard publisher and must not be cited as proof of this design.

The GitHub App user-token installer is limited to user-triggered setup and protected configuration pull requests. Autonomous execution requires the dedicated App controller and short-lived installation tokens. The broad OAuth fallback remains observe-only.

Every hosted route that can contact GitHub or OpenAI first verifies Vercel Production Git provenance for protected `LeChiffreVol2/changeplane` `main`. Preview, fork, CLI, and unattributed deployments fail closed before an authorization redirect, token exchange, repository lookup, provider call, or repository mutation.
