# Agentic SDLC: diagnosis and recovery design review

Review date: 2026-09-10. Examined source: `eaa791c78e03f6cc375f16bf5162f04e670e184a`. Status: the owner approved the combined design; implementation and capability qualification are in progress. Findings below describe the examined baseline. See [recovery core](recovery-core.md) for new source behavior and qualification boundaries.

## Accepted direction

The owner selected two outcomes: reduce human work in PR/CI recovery using measurable diagnosis and recovery, without increasing false assurance; and make the core independently operable by individuals and organizations, with hosted operation optional. [ADR-0008](adr/0008-operator-owned-open-source-recovery.md) records this architectural direction. Budget is USD 0 now; USD 100 applies only when scaling.

The owner expanded the target to GitHub, GitLab and Cursor Origin (Q3), including agent-independent PR/MR workflows. [ADR-0009](adr/0009-multi-forge-assurance-boundaries.md) records that direction. The authoritative forge owns merging; an authoring surface or mirror does not acquire that authority through a matching repository name or commit SHA. This changes the target architecture while the shipped release remains GitHub-specific.

The owner accepts multiple tested-subject forms (Q4). Source-head, test-merge, merge-batch and artifact evidence must retain their actual subjects, provenance and relationships; their inclusion never makes them interchangeable. The owner delegated the first qualification gate and suitable sequencing (Q5); the proposal below uses conformance cases plus real consumer installations, with unsupported or inaccessible capabilities explicitly excluded from release claims.

Auto-repair is opt-in per repository (Q6). The intended default is diagnosis and bounded transient recovery. Models propose; the deterministic harness decides; a separately authorized controller applies. Source repair remains limited to two attempts in one immutable fifteen-minute campaign. Protected tests, evidence policy, workflows and manifests still need human review. A qualified adapter and operator installation are prerequisites even when an owner enables repair. These constraints are settled; exact transient-recovery eligibility still needs a falsifiable implementation contract.

The owner selected CI-first operation with a local evaluator and a separate controller where writing or Guard publication requires it (Q7). Reports and evidence stay in the user's machine/CI, with no automatic telemetry to ChangePlane; explicitly enabled model features use the user's key and bounded filtered context, and incident sharing is voluntary (Q8). Fork PRs/MRs enter the next read-only diagnosis/handback scope; cross-repository patch application remains outside this milestone (Q9). These decisions complete the interview frontier; the owner subsequently confirmed the combined design with “approve”.

## Proposed core boundary

```text
GitHub collector ─┐
GitLab collector ─┼─> Observation + CollectionOutcome
Origin collector ┘                 │
                                   v
                    pure validate / match / assess
                                   │
                         Assessment + Handback
                                   │
                  separately authorized recovery controller
```

Collectors own provider authentication, pagination, bounded safe-read retries, execution lineage, capability discovery and canonical-state revalidation. A configured trusted origin determines where credentials may be sent. Webhooks are signals to re-observe canonical state; duplicates, delivery delay and ordering cannot create freshness.

The versioned observation carries change identity; distinct revision roles; typed tested subject; producer, execution and configuration identity; native outcome and bounded diagnostic facts; collection completeness, observation time and optional verified subject relationships. Retain unknown explicitly. In the pure evaluator, observation content can support an advisory assessment; authenticated collection and qualified authority are additional prerequisites for enforcement or mutation. Preserve the existing v1 GitHub reader interface through a compatibility adapter.

The evaluator separates **assurance disposition** from **diagnostic evidence**, **causal hypotheses**, **recovery disposition** and **notification delivery**. A cancellation is not evidence that application code is wrong. Flakiness requires repeated, comparable observations; one successful rerun cannot erase a failed attempt or prove a root cause. A handback names the exact change, trusted policy and scope, evidence locators, allowed action and remaining budget without requiring prose interpretation.

Transient recovery needs its own bounded policy: initially retry classified safe reads under provider rate guidance; request a CI rerun only for qualified transient classes, unchanged subject/policy, a permitted trusted job and an explicit recovery budget. Do not blindly rerun jobs with unqualified deployment or other external side effects. Permissions, invalid configuration, ambiguous publication and unknown causes require a specific handback or containment. A rerun request is not successful recovery; success requires newly observed evidence. Neither a read retry nor an event replay resets the source-repair campaign.

Operator configuration must bind the operator's trusted source/release, credential audience, installation, allowed repositories and independently authorized publisher/controller. Making the current vendor URL and repository constants editable is not sufficient. Any writing deployment needs qualification for concurrent generations, uncertain writes, revoked authority and restore behavior before it can operate unattended. CI-first does not imply that arbitrary CI output is trusted or that GitHub concurrency alone fences a stalled external writer.

Under Q7–Q8, the local/CI evaluator needs no hosted ChangePlane account or central telemetry. Diagnostics use allowlisted structured fields and bounded evidence references; secret redaction is necessary but cannot make an entire raw log or agent trajectory safe to publish. Retention follows the operator's explicit local/CI artifact policy and the selected provider's actual terms. Source and logs leave that boundary for a model only after the relevant feature is enabled, using permitted context and the user's credential. Public benchmark submissions require a separate deliberate export with synthetic or reviewed sanitized data. Do not claim zero retention.

Under Q9, fork collectors read trusted target-repository policy and canonical provider metadata without running fork-controlled code, CI configuration or instructions in a privileged context. Missing permissions or unavailable fork evidence yield a specific handback, not an expanded token or a satisfied decision. Returning a handback artifact does not itself authorize posting comments or writing the contributor's branch.

## Proposed first measurable gate

The owner delegated a suitable benchmark and live-installation gate (Q5). Qualify individual capabilities, rather than waiting to claim all forges and all authority levels at once. Keep the current USD 0 constraint; neither paid GitLab features nor Cursor access nor model calls may create new spend during this qualification.

1. **Versioned conformance corpus.** Publish at least thirty independently labeled cases spanning behavioral failure, transient infrastructure, permissions/configuration, unknown cause, incomplete observations, stale heads, same-SHA retries/generations, protected control changes, tested-subject mismatch and mirror/artifact provenance. Include expected disposition, permitted action and oracle rationale, rather than deriving expected answers from the implementation. Deterministic proposal fixtures qualify the harness only; they do not establish live model performance.
2. **Safety and recovery acceptance.** The corpus must contain zero false satisfied decisions and zero source-repair requests for cases labeled environmental, permission-related, stale, protected or unknown. Every automatic action must remain within its declared authority and immutable budget. A recovered case needs fresh evidence; contained cases need an accurate reason and next action. Zero errors on this corpus is a test result, not a population-wide guarantee.
3. **Real consumer installations.** Use immutable release references in synthetic GitHub personal and organization consumer repositories and a GitLab.com Free consumer project, using available accounts and free capacity. Exercise failure, rerun, new revision, missing association, token denial and installed output parity; record actual execution identities. Existing owner evidence may be reused only for the exact qualified behavior. Create/delete test resources only within the user's authorized scope and preserve unrelated projects. GitLab installation qualification remains pending access to a suitable account/project.
4. **Paired outcome measurement.** Compare a frozen current reader/manual-triage baseline with the candidate on the same incidents. Report human intervention count, time to a correct next action, observed recovery time, wrong repair requests, false blocks, runner usage and coverage. Require fewer human interventions on the predeclared recoverable incident set, with no new incorrect decisions and no unbounded resource use. Report inconclusive cases and scheduler delays; an eligible five-minute timer is not a recovery-time guarantee.
5. **Capability-specific publication.** A reader can ship after its read-only gate; Guard publication and repair require additional operator isolation, ambiguous-write, revocation and restore drills. Native Origin and inaccessible paid/self-managed paths remain documented targets with contract fixtures until live qualification exists. Competitive claims require a measured scenario and comparable baseline under ADR-0005.

The live installation gate demonstrates integration behavior, not customer demand. External user outcomes and a paid business model remain separate later validation.

USD 0 is the current ChangePlane spending constraint. CI usage is bounded by each operator's plan and quota; optional BYOK model use may cost that operator money and must be described accordingly. No new subscription, managed model spend or paid infrastructure is part of this design-review task.

## Candidate implementation slices, pending decisions

1. A typed failure observation and portable handback: preserve raw outcome, distinguish evidence from causal hypotheses, allow unknown, name one permitted next action, and bind the entire handback to target/policy/evidence.
2. Explicit tested subjects and provider collectors: distinguish proposed change, trusted policy revision, actual tested subject and native authority; preserve stronger provenance separately from provider metadata association.
3. A public recovery conformance corpus plus downstream consumer qualification: independent expected outcomes, adversarial stale/ambiguous evidence, environmental failures, and a repeatable comparison with today's reader/manual process.
4. An operator-owned trust boundary and qualified recovery procedure: only after publication, credential isolation, ambiguous writes and restore behavior have an evidenced design. Keep this obligation separate from immediate read-only adoption.
5. Later investigations: independently bound prior intent, baseline-versus-candidate behavioral validation, and links to released artifacts and customer-provided incident evidence. Incident linkage does not establish causality or retroactive PASS.

These are proposed implementation boundaries and sequence under the accepted direction; the owner has confirmed the combined scope; implementation details remain subject to validation. Adding models, longer retry budgets or an orchestration service would not by itself address the observed causes.

## Combined proposal for final confirmation

Build an operator-owned, open-source diagnosis and bounded recovery core for change requests, independent of the authoring agent, with GitHub/GitLab/Origin adapters and explicit per-provider capabilities. Start with the pure observation/evaluation/handback boundary, a frozen conformance corpus and qualified GitHub/GitLab readers, including read-only fork contributions. Keep subject provenance, policy trust, publisher authority and merge enforcement distinct. Unknown evidence stays unknown.

Use local execution and existing CI as the default operating surface. Add independent publication/application authority only where its credentials, concurrency and failure recovery have passed qualification. Enable source repair separately per repository; retain the two-attempt/fifteen-minute campaign and protected-path review. Keep diagnostics with the user and make model egress and incident sharing explicit choices.

Measure reduced human recovery work against a recorded baseline and publish exact capability evidence. Do not require paid services for this milestone; leave native Origin and inaccessible provider paths unqualified until they can be exercised. Finish these bounded capabilities before adding broader planning, deployment or incident orchestration. The final confirmation concerns this combined scope, not a claim that the engineering or live qualification has already been completed.

## Primary-source comparison

Sources reviewed 2026-09-10; access dates do not imply publication dates. These sources provide design precedents, not evidence of ChangePlane superiority.

- [Inspect errors and limits](https://inspect.aisi.org.uk/errors-and-limits.html) and [OpenHands events](https://docs.openhands.dev/sdk/arch/events): preserve distinct failure states and attempt history. A causal explanation remains a hypothesis until supported by evidence.
- [SWE-bench harness](https://www.swebench.com/SWE-bench/reference/harness/) and [grading](https://www.swebench.com/SWE-bench/api/harness/): compare failure-to-success behavior and preservation of previously passing behavior under recorded evaluation environments.
- [SWE-agent trajectories](https://swe-agent.com/latest/usage/trajectories/) and [OpenHands persistence](https://docs.openhands.dev/sdk/guides/convo-persistence): make recovery context portable, but do not import whole sessions containing credentials or broad private context.
- [SLSA build provenance](https://slsa.dev/spec/v1.2/build-provenance) and [in-toto Statements](https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md): bind process claims to digest-identified subjects. Origin and process evidence are distinct from behavioral correctness.
- [GitHub required-check troubleshooting](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks) and [rerun semantics](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs): exercise ambiguous, skipped, stale and repeated evidence explicitly.
- [GitLab MR API](https://docs.gitlab.com/api/merge_requests/), [MR pipelines](https://docs.gitlab.com/ci/pipelines/merge_request_pipelines/), [merged results](https://docs.gitlab.com/ci/pipelines/merged_results_pipelines/) and [merge trains](https://docs.gitlab.com/ci/pipelines/merge_trains/): preserve revision roles, source/configuration trust, actual pipeline subject and paid-feature boundaries.
- [GitLab Jobs API](https://docs.gitlab.com/api/jobs/), [job artifacts](https://docs.gitlab.com/api/job_artifacts/) and [CI includes](https://docs.gitlab.com/ci/yaml/): preserve current execution lineage, artifact provenance and transitive execution-policy dependencies.
- [GitLab external statuses](https://docs.gitlab.com/ci/ci_cd_for_external_repos/external_commit_statuses/), [merge checks](https://docs.gitlab.com/user/project/merge_requests/auto_merge/#require-a-successful-pipeline-for-merge), [status checks](https://docs.gitlab.com/user/project/merge_requests/status_checks/), [response authorization](https://docs.gitlab.com/api/status_checks/#set-status-of-an-external-status-check) and [protected branches](https://docs.gitlab.com/user/project/repository/branches/protected/): inspect native enforcement and override/publication authority independently.
- [GitLab approval settings](https://docs.gitlab.com/user/project/merge_requests/approvals/settings/), [fine-grained job permissions](https://docs.gitlab.com/ci/jobs/fine_grained_permissions/), [webhooks](https://docs.gitlab.com/user/project/integrations/webhooks/) and [commit-status API](https://docs.gitlab.com/api/commits/#set-commit-pipeline-status): do not infer exact-revision approval, full reader credentials, exactly-once delivery or same-SHA writer fencing.
- [Origin overview](https://cursor.com/docs/origin), [GitHub mirroring](https://cursor.com/docs/origin/mirror-github), [native PRs](https://cursor.com/docs/origin/pull-requests), [API](https://cursor.com/docs/api/origin) and [API changelog](https://cursor.com/docs/api/origin/changelog): distinguish native forge authority from mirror observations; current documentation does not replace live qualification.

Any future competitive claim must identify the scenario, baseline, version, configuration, labeled cases, observation source, false decisions and human intervention cost, consistent with [ADR-0005](adr/0005-scenario-scoped-competitive-claims.md).
