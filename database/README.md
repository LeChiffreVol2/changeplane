# Candidate databases

The commercial store and Guard publication journal have different authority, durability, and deletion requirements. Neither is activated by the presence of a migration or connection string.

## Guard publication journal

The candidate [002_guard_publication_journal.sql](002_guard_publication_journal.sql) migration and [server adapter](../server/guard-publication-journal.js) hold durable exclusive ownership for one authenticated repository and revision fingerprint during a Guard mutation. The `changeplane_guard` schema is an authority store, not the commercial event store. Enrollment binds tenant, installation, Guard App, exact protected source release and epoch. Occupied or poisoned lanes do not expire; uncertain writes remain blocked until prior writers are fenced. A successful operation releases its own lane only after all GitHub writes and response validation finish.

Read the [Guard publication journal operating design](../docs/guard-publication-journal.md) before applying a journal migration or enrolling a repository. It defines role isolation, metadata limits, finite admission/storage/cost budgets, operator billing ownership, credential rotation, retention, incident handling, and required drills. Use separate authority credentials and a dedicated authority database by default. Reusing commercial infrastructure requires a separate reviewed isolation decision.

Hosted Production requires the journal for all Guard writes, including owner-canary writes. `CHANGEPLANE_GUARD_JOURNAL_ENABLED`, `CHANGEPLANE_GUARD_JOURNAL_DATABASE_URL`, `CHANGEPLANE_GUARD_JOURNAL_EPOCH`, and `CHANGEPLANE_GUARD_JOURNAL_VERIFIED_RELEASE` must match the reviewed deployment and database enrollment. Missing, disabled, unhealthy, or mismatched configuration stops publication; it never falls back to the unjournaled publisher. Do not promote this candidate before database enrollment and a separate new Guard App are ready. A rollback must preserve the same authority boundary or leave publication paused. Customer serialization gates still require live evidence.

The parser requires enabled `true`, a PostgreSQL URL whose only query pair is `sslmode=verify-full` (not `require`), an epoch UUID, a distinct Guard App, and an exact 40-character verified release matching the current source SHA. Duplicate or extra URL options, fragments, and encoded hosts are rejected. Every `VERCEL=1` Guard path requires the journal; external access also requires Production provenance. Readiness's `guardJournalConfiguration` and `guardJournalConfigured` fields validate supplied configuration only. They do not connect to the database or establish enrollment, provider health, zero-loss authority history, or live serialization. `guardPublicationSerialized` remains false pending that evidence.

Authority recovery requires zero loss of acknowledged exclusion decisions, or a halt followed by a new Guard principal and freshly approved publisher binding. An old backup, changed epoch, cleared lane, or commercial-store restore test cannot prove that a previously dispatched GitHub write is fenced. Commercial deletion and retention jobs must never remove uncertain journal rows or their enrollment. Live customer gates remain closed until the exact implementation and operating environment are proven.

## Commercial plane

`001_commercial_plane.sql` remains the earlier candidate telemetry/Fleet schema. Its `server/commercial-store.js` usage projection attributes each generation to its earliest retained occurrence in UTC; late events and retention can change that count. It is not the quota or invoice authority.

The [003_pilot_admission.sql](003_pilot_admission.sql) candidate and [server/pilot-admission.js](../server/pilot-admission.js) adapter use the separate `changeplane_commercial` schema for operator-enrolled contracts, repository bindings, immutable admission receipts and authoritative monthly counters. `createPostgresPilotAdmission` exposes `admitEvaluation`, `readAdmission` and `readUsage`; it has no enrollment or pruning method. Contracts are active for no more than 30 days and specify finite included use, bounded grace and repository limits. This slice supports Verify Lite pull-request pilots with Strict Head only. It does not enable the Free/public catalog, Queue Certified, general commercial outcomes or automated billing.

The server supplies the authenticated tenant, repository, Guard installation/App, revision fingerprint and Evaluation Generation. It obtains `workflowStartedAt` from live exact GitHub run-attempt metadata after validating OIDC repository, run, attempt, workflow path and event; request timestamps are ignored. New admission requires both the verified workflow start and database admission time to fall inside the active contract window, and rejects a start later than database time. Admission checks the registered binding and allowance atomically, inserts one receipt and increments one tenant/month counter. The database fixes the UTC period and counter ordinal at admission, and the receipt preserves the verified workflow start. An exact duplicate returns the original receipt even after expiry; it does not consume another unit. Completion and recovery reuse admission without recharging or rechecking contract expiry, while current GitHub authority, managed policy and exact-head evidence still apply. Altering a generation's target or binding must be rejected.

Before any commercial lookup or database wait, the Guard controller retires earlier usable success and confirms the new generation's `in_progress` Guard inside its journal lane. Worker loss during the wait therefore leaves a blocking Guard and held publication authority. An uncertain database commit may have consumed a unit; the adapter attempts to resolve the immutable receipt without repeating the admission mutation or refunding automatically. Missing entitlement, exhausted allowance or a storage outage cannot produce PASS. The controller publishes `action_required` for the admission block, then returns HTTP 402 for denied allowance or 503 when allowance cannot be confirmed only after acknowledged publication and journal release. Unavailable publication authority remains blocked. A resource admission receipt is not proof of a completed evaluation or an invoice item.

The pilot runtime uses checked RPCs and tenant reads behind forced RLS. It cannot modify contracts or enrollment, write counters directly, refund/reset usage, delete receipts, or assume the transition owner role. Tenant context comes from authenticated GitHub identity; setting a database tenant variable is not authentication. Hosted configuration rejects reuse of the journal's normalized host, port, database path and username, even with a different password or protocol alias. Different URLs do not prove separate privileges: the pilot credential must have no Guard-journal access, and commercial restore/deletion jobs must never alter journal authority.

Every administrative enrollment insert, update or delete must begin a transaction, lock the affected tenant contract `FOR UPDATE`, perform the change and commit while retaining the lock. For a transfer, lock both affected tenants in ascending ID order. Admissions already take that contract lock; locking only one enrollment row would not serialize changes to other repositories counted against the cap. This is a required operator protocol, not a runtime enrollment feature or an automatic trigger. Test it with concurrent admission and operator transactions before activation.

Readiness reports `pilotAdmissionConfiguration`. When admission is requested, missing or mismatched release configuration, unsupported TLS options, or reuse of the journal's login on the same host/port returns `configuration_required`. A different selected database does not make a reused cluster login independent. This is a configuration check only; distinct URLs cannot prove role isolation, enrollment, database health or production operating readiness.

Before any activation, the release owner must:

1. Review migrations, actual roles/grants, the minimal metadata inventory and finite repository, connection, storage, transaction-rate and provider-cost budgets. Do not store source, names, prompts, patches, credentials or customer business data.
2. Verify two-tenant isolation and mismatched installation/App rejection in PostgreSQL, concurrent admission at the final allowed unit, exact retries, unknown-commit recovery, month boundaries, disabled/expired contracts and immutable receipt/counter behavior after telemetry deletion.
3. Prove restore and credential rotation preserve accounting, and reconcile uncertain admissions before treating counters as invoice evidence. Invoicing remains a separately reviewed manual operation; no provider or billing service is created here.
4. Verify operator-controlled pruning: pilot receipts have a proposed 90-day maximum and counters a proposed 13-month retention period. The verified attempt-start constraint prevents a run behind a 90-day receipt from entering any currently active contract of at most 30 days, including renewal. Before deleting receipts, close their contract/enrollment and verify the source rule through clock, renewal and replay drills. Demonstrate the deployed pruning procedure before activation; source constraints alone establish no live retention guarantee. Runtime callers have no pruning authority.
5. Complete tenant deletion, backup handling, exact-release legal review and live canary evidence. The legal entity and effective retention/deletion obligations remain unresolved drafts; these source targets are not customer guarantees.

See [ADR 0002](../docs/adr/0002-minimal-commercial-event-store.md) and the [retention approval draft](../docs/retention-deletion.md). No live commercial database is provisioned or paid launch established. `commercialReady` remains false while `commercialRuntimeIntegrated` and `guardPublicationSerialized` remain false in code; configuration flags and release attestations cannot substitute for the missing general runtime and live operating evidence. GitHub remains the repository, Check, Ruleset and merge authority.
